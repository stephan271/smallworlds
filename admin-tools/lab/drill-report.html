SmallWorlds Backup Drill

The whole backup chain, exercised end to end on a throwaway cluster with Immich as the worked example — from photo upload to a member's home device and back again.

Cluster k3s on LAN node, built from scratch Assets 20 photos Findings 5 Restores proven 2

Why this ran

doc/storage-and-backup.md §5 has carried the same item for months: “Restore path is untested. The procedures in §7 have never been exercised end-to-end.” Everything the document says about backups was derived from reading manifests, not from watching bytes move. That is exactly the kind of claim that stays true-looking until the day it matters.

So the chain was rebuilt on a disposable cluster and driven with real data: upload photos into Immich, let every backup mechanism act on them, pull them onto a simulated home device, then delete things and put them back. Five discrepancies between the documents and the behaviour turned up, two of which affect the production cluster today.

The chain as it actually behaves

What the drill proved

Two of these had never been done before. The rest re-confirm, on a cluster built from nothing, what the August staging run already established — worth having, but not news.

New

  • ✓The database restores from barman. recovery cluster bootstrapped from s3://postgres-backups/immich-database/ with all 20 assets — §7.1 works as written, and had never been executed
  • ✓Deleted originals come back from the member's device. 5 files deleted from the library, restored from the home copy, and Immich served one back byte-identical to its manifest digest — no procedure for this existed

Re-confirmed on a fresh cluster

  • ✓Immich's schema coupling holds on v3.0.0. table asset, all ten columns, originalPath rooted at /data/upload/<user>/xx/yy/<uuid>.jpg — previously verified against production in August; this re-checks it against the image the chart currently pins
  • ✓Export is idempotent without any read grant. first run: 20 appended · second run: 0 appended, 20 already present, 0 errors
  • ✓Every authorization boundary refuses correctly. device write 403 · device reading another pod 403 · agent read 403 · re-append 409 · bad token 401 · DELETE 501
  • ✓A rewritten history stops the device. forged entry with a recomputed self-hash still broke the chain at seq 6; agent exited 2, kept 5 valid objects, changed nothing local

Findings

Ranked by what they cost if left alone. The first two affect the production cluster now.

High

Every database backup runs hourly, not daily

CloudNativePG's schedule takes a six-field cron with seconds first. All six tenants write a five-field one, so "0 2 * * *" parses as second 0, minute 2, every hour.

lastScheduleTime: 2026-08-14T13:02:00Z nextScheduleTime: 2026-08-14T14:02:00Z ← one hour, not one day two completed base backups within 10 minutes 259 MB in postgres-backups from an *empty* database

Fix: "0 0 2 * * *" in all five tenant clusters, "0 0 3 * * *" for Keycloak. Until then each cluster takes ~24 base backups a day, ~144 across the community, all held for 7 days on a shared 200 GB volume.

High

Members' personal pods are replicated offsite

Three documents state the pod-gateway bucket stays on-cluster. But the replicator runs rclone sync source: dest: across the whole instance, and the setup instructions grant the replicator key read on every bucket in a loop — so following the documented procedure ships the pods to a third-party provider, unencrypted.

pod-gateway/<user>/objects/immich/2025/2025-10-18/…jpg: Copied (new) … all 40 pod objects and manifest entries copied offsite

Fix: decide which document is right. If pods must stay put, drop that bucket from the key's grants and say so in the README; if they should go offsite, correct doc/storage-and-backup.md §4/§7 and doc/pod-archive.md. Note the pod design's privacy intent and that objects are unencrypted at rest — this includes the immich-locked/ prefix.

Medium

Garage has never used its 120 GB volume

apps/garage.yaml sets persistence.size and persistence.storageClass, neither of which exists in chart 0.7.1 — the real keys are nested per volume (persistence.data.*, persistence.meta.*). Helm ignores unknown values silently.

data-garage-0 Bound pvc-8029f1bb… 1Gi local-path garage-data-pv 120Gi Available ← never bound corroboration: an earlier real install left /mnt/smallworlds-data/garage at 0 bytes

Fix: move the keys under persistence.data; keep meta on fast local storage. Correct the storage table in §2, which claims Garage data lives on the static PV. Impact is limited on Hetzner — local-path sits on the same volume via the k3s symlink — but the declared budget is fiction and the PV is dead weight.

Medium

Auto-created offsite buckets have no versioning

The setup guide offers letting rclone create the destination buckets on first sync. Buckets made that way are un-versioned, which removes the one property that makes the offsite leg a backup rather than a mirror.

created precious.txt → synced → deleted cluster-side → re-synced offsite after the deletion: (empty) mc version info: off/immich is un-versioned

Fix: require pre-created versioned buckets and a verification step. §3 already warns that a plain mirror propagates mass deletion within 24 h; the setup instructions quietly permit exactly that.

Medium

No written way to get the photos back

ADR 0047 removed Immich from pv-backup, making the pod archive the only server-side copy of the pixels — but §7 has no procedure for restoring them. The archive alone is not enough: its keys are human-shaped (immich/<year>/<date>/<id8>-<name>) while the library is UUID-shaped, and only the database holds the mapping.

restored 5 originals · sha256 verified against the manifest Immich served the asset back: http=200, digest identical

Fix: adopt the procedure written and proven here as §7.5 — restore the database first, dump an inventory, map keys, copy back, verify. Worth stating plainly that pixel recovery requires a working database backup.

Reproducing it

The harness lives in admin-tools/lab/ and rebuilds the whole thing from an empty machine.

# 1. k3s with the real storage contract (node name, /mnt/smallworlds-data, etcd off the bulk disk)
sudo bash admin-tools/lab/lab-node-bootstrap.sh

# 2. cloudnative-pg + Garage + the static PVs, with the corrected chart values
admin-tools/lab/p1-infra.sh

# 3. Immich, via a lab overlay over the real tenant manifests
kubectl kustomize --enable-helm admin-tools/lab/immich | kubectl apply -f -
python3 admin-tools/lab/seed-immich-photos.py

# 4. the pod archive, then a simulated home device
./admin-tools/pod-enroll-device.sh --agent immich --env lab
./admin-tools/pod-enroll-device.sh --user <id> --name lab-pi --env lab --url http://127.0.0.1:8080
admin-tools/lab/sim-device.sh sync && admin-tools/lab/sim-device.sh verify
immich/kustomization.yaml
The overlay. Four patches, each a stated lab concession: no Keycloak, no ML models, in-cluster gateway URL, stub OIDC secret.

Runs the unmodified pod-agent.py as an ordinary user against its own data directory — the protocol is faithful, only the systemd packaging is skipped.

What this drill did not cover

Only Immich was exercised. pv-backup was not: its only consumers are Nextcloud and Forgejo, so a wider tenant set is needed to test it honestly. Velero was deployed but no namespace restore was attempted, which matters because its stated value is recovering runtime-generated secrets — including the trap noted in §7.1, where a restored database still holds the old password while the operator generates a new database-app secret.

The offsite target was a local MinIO standing in for Backblaze B2, so provider-specific behaviour — object lock, lifecycle rules, B2's own versioning semantics — remains untested. And nothing here was run against production; the two high findings were reproduced from the manifests the production cluster deploys, but the live cluster was down during this work and should be checked directly once it is back.
