# Backup data is physically separated from operational data in a second Garage instance

Backup data will live on its own block volume, served by a second Garage instance (`garage-backup`) whose metadata *and* data directories both sit on that volume, while the existing instance keeps only the buckets that are primary application storage — `nextcloud`, `forgejo`, `plane`. Today a single 200 GB volume holds the Immich library, every CloudNativePG data directory, every `local-path` claim, and all of Garage, so the first hop of every backup chain shares a failure domain with the data it protects; nothing on the cluster enforces a size, which means one runaway consumer can starve the very backups meant to recover from it. Two instances are required rather than one relocated instance because Garage has no per-bucket placement — one instance means one `data_dir` — and because the operational buckets are not backups at all but the primary store for users' Nextcloud files, so moving all of Garage to the backup volume would merely relocate primary data next to the backups instead of separating them. The metadata directory moves with the data: Garage's LMDB index is what resolves a bucket and key to content-addressed blocks, so leaving it on fast operational storage — which the chart's own values comment invites — would leave the backup volume holding an unreadable pile of blocks after exactly the failure this decision exists to survive. Because both volumes attach to one machine, this separation addresses disk failure and capacity starvation but not node loss, compromise, or provider failure, so the offsite leg remains enabled by default rather than becoming optional; it is instead scoped to an explicit bucket list that excludes `pod-gateway`, which restores the intent stated in `docs/adr/0047` and violated in practice by a whole-instance `rclone sync` combined with setup instructions that grant the replicator read on every bucket. The offsite copy of the databases is load-bearing beyond its own contents: Immich stores pixels under asset UUIDs and Nextcloud stores objects as `urn:oid:<fileid>`, so PostgreSQL is the index without which neither file backup can be restored to anything a person recognises. Nextcloud's bucket gains a server-side copy into `garage-backup`, having previously had no backup other than the offsite mirror. Restores read from `garage-backup` — including Immich originals, which are recovered from the `pod-gateway` bucket rather than from a member's hardware — and members' home devices become strictly the disaster tier, used only when both volumes are lost. This amends the failure-domain accounting in `docs/adr/0047`, which accepted Immich pixels existing only on the node disk and on home devices: they now exist in three domains, with the pod bucket on separate storage, at no cost in duplicated bytes on the same disk since the copy that was removed there is not reintroduced.
