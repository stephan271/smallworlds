# Database backups move to the Barman Cloud plugin before CloudNativePG removes the in-tree implementation

Every database Recovery Point this project produces is written by CloudNativePG's in-tree Barman Cloud support — `spec.backup.barmanObjectStore` on the four tenant clusters and on `keycloak-db` — and every restore reads it back through `externalClusters[].barmanObjectStore`; that implementation is deprecated in CloudNativePG 1.30, which the operator announces as an admission warning on any manifest still using it, and it is removed completely in 1.31.0. The consequence is not a deprecation to schedule at leisure but a specific and quiet catastrophe: a routine operator upgrade — precisely the kind the in-cluster Renovate CronJob proposes every Monday — silently removes both the only mechanism producing database Recovery Points and the only mechanism for reading the ones already written, and because a cluster whose backups have stopped looks exactly like a cluster whose backups are working, the loss would most likely be discovered during a restore, which is the one moment at which nothing can be done about it. PostgreSQL is additionally the index for nearly every file restore here — Immich stores pixels under asset UUIDs and Nextcloud stores objects as `urn:oid:<fileid>` — so losing the database chain does not cost one dataset but renders the surviving object copies unreadable to a human, which is why this ranks above every other outstanding backup task including the offsite leg. The migration is therefore ordered ahead of the upgrade rather than bundled with it: install `plugin-barman-cloud` into the operator's namespace (it requires cert-manager, which this cluster already runs, and CloudNativePG 1.26 or newer, which 1.30.0 satisfies), declare an `ObjectStore` of `barmancloud.cnpg.io/v1` **per namespace** — six, not the two this decision first assumed, because the resource is namespaced and a `Cluster` can only reference one beside it, so the five tenants sharing the `postgres-backups` bucket each need their own object naming the same destination and differing only in `serverName`, while `keycloak-db` keeps the separate bucket and credential it has always had — and reference them from each `Cluster` through `spec.plugins` with `name: barman-cloud.cloudnative-pg.io`, `isWALArchiver: true` and `parameters.barmanObjectName`, remembering that every `ScheduledBackup` must also gain `method: plugin` and `pluginConfiguration.name` or it will keep firing on schedule while taking nothing at all, and that recovery moves from `externalClusters[].barmanObjectStore` to `externalClusters[].plugin` carrying `barmanObjectName` and the unchanged `serverName`. Continuity of the existing archives is a requirement rather than a hope: `destinationPath`, the per-tenant `serverName` of `<tenant>-database`, and the bucket names stay exactly as they are, so that the archives written by the in-tree implementation remain restorable by the plugin, and the successful end-to-end restore drill of 2026-08-16 — a `database-restore` cluster bootstrapped from `s3://postgres-backups/` on `garage-backup` that recovered the Nextcloud database with zero data loss across a WAL replay spanning an hour — is the baseline any post-migration drill must reproduce before the in-tree configuration is deleted. One Garage-specific property must survive the move and must be proven rather than assumed: the signing region, carried today as `AWS_REGION` and `AWS_DEFAULT_REGION` set to `garage` in each `Cluster`'s `env`, because Garage answers a request signed for any other region with HTTP 400 and that exact mismatch is how the 2026-08-09 production outage began, filling the disk with WAL that could not be archived; the plugin does **not** inherit it, because it runs barman in a sidecar rather than in the instance, so the region is declared on the `ObjectStore` under `spec.instanceSidecarConfiguration.env` and the `Cluster`'s own `env` block is removed rather than left behind to look load-bearing. Until the migration is drilled, the CloudNativePG chart version is pinned and the Renovate proposal that bumps it is not merged, since accepting that bump first is the single action that converts a scheduled piece of work into an unrecoverable one.
